**กลุ่มเป้าหมาย:** Developer  
**ระยะเวลา:** 10–20 นาที  
**เครื่องมือ:** อนุญาตให้ใช้ AI  
**ข้อมูลตั้งต้น:** โจทย์ใน README ผู้สอบสร้างโปรเจกต์เอง

## 1. สิ่งที่ต้องการประเมิน

| สิ่งที่ประเมิน | พฤติกรรมที่คาดหวัง |
|---|---|
| ทำความเข้าใจโจทย์และจัดลำดับงาน | แยกข้อกำหนดหลักและเลือกทำส่วนสำคัญได้ภายในเวลา |
| ใช้ AI ในการพัฒนา | ให้บริบทและข้อจำกัดแก่ AI ตรวจโค้ดที่ได้ และปรับคำสั่งหรือแก้ไขเมื่อพบปัญหา |
| สร้าง workflow | ใช้ LangGraph เลือกและเรียก specialist ตามลำดับ แล้วรวบรวมคำตอบ |
| ตรวจสอบพฤติกรรม | ตรวจการเลือก specialist ผลลัพธ์ สถานะ และ trace รวมถึงกรณีไม่มี specialist ที่ตรง |
| จัดการข้อจำกัดและความปลอดภัย | ตรวจ calculator ด้วย restricted AST จัดการ credential และไม่อ้างว่ามีข้อมูลสดหากไม่ได้ค้นจริง |
| ส่งมอบงาน | มีวิธีติดตั้ง รัน และตรวจสอบที่ทำตามได้ พร้อมระบุส่วนที่ยังไม่สมบูรณ์ |

## 2. พฤติกรรมที่ใช้ประเมิน

| กรณี | วิธีตรวจและผลที่คาดหวัง |
|---|---|
| คำขอที่ตรงหลาย specialist | ใช้ `Research LangGraph, calculate (12 + 3) * 4, then summarize.` ต้องเลือก `research`, `calculator`, `summarizer` ตามลำดับ ไม่ซ้ำ และคำนวณได้ `60` |
| Trace | จากกรณีข้างต้น ต้องเห็นขั้นตอนเลือก specialist, specialist ทั้งสาม และขั้นตอนรวบรวมคำตอบ พร้อมสถานะ |
| Research: LLM จริง | ให้ถาม `What is LangGraph?` ตรวจว่ามีการเรียก LLM ด้วยค่าจาก `.env` และแสดงคำตอบที่เกี่ยวข้อง โดยไม่ตัดสินจากข้อความที่ต้องตรงกันทุกคำ |
| Research: กรณีผิดพลาด | จำลอง LLM ล้มเหลวหรือตั้งค่า endpoint ผิดในการทดสอบแยก ต้องแสดงสถานะล้มเหลวและข้อความที่เข้าใจได้ โดยไม่เผย credential |
| คำขอที่ไม่ตรง | ทดลอง `hello` ต้องแสดง fallback ที่ระบุประเภทคำขอที่รองรับ |
| Calculator: input ไม่ปลอดภัย | ทดลอง input ที่มีการเรียกฟังก์ชัน เช่น `calculate __import__("os")` ต้องไม่รันโค้ด และแจ้ง input ไม่ถูกต้อง |
| Calculator: ขอบเขตเลขชี้กำลัง | ทดลอง `calculate 2 ** 101` ต้องปฏิเสธ และ `calculate 2 ** 3` ควรได้ `8` |
| การตรวจสอบ | ทดสอบพฤติกรรมโดย mock LLM ทั้งกรณีสำเร็จและล้มเหลวโดยไม่ใช้ key หรือเครือข่าย และทดสอบ LLM จริงแยกต่างหากเมื่อบริการพร้อม |

ตรวจซอร์สโค้ดประกอบเพื่อยืนยันการใช้ LangGraph และ restricted AST รวมถึงตรวจว่าไม่มีการใช้ `eval`, `exec` หรือ shell execution เพื่อประมวลผลนิพจน์ การเรียก specialist ภายใน node ตามลำดับถือว่าผ่านได้ ไม่จำเป็นต้องสร้าง graph แบบ parallel หรือ dynamic branching

ต้องมีเว็บและแสดง workflow ให้เห็นภาพตาม README ผู้จัดสอบควรเตรียม Python, dependency, `.env` ที่มี `LITELLM_BASE_URL`, `LITELLM_API_KEY`, `LLM_MODEL` และตรวจการเชื่อมต่อบริการก่อนเริ่มจับเวลา ห้ามนำ credential จริงไปใส่ในผลการทดสอบหรือเอกสาร หากบริการ LLM ล่ม ให้ประเมินจาก mock และโค้ดที่ส่ง พร้อมบันทึกว่าไม่ได้ยืนยันการเชื่อมต่อจริง

## 3. เกณฑ์การให้คะแนน

| หัวข้อ | คะแนน | แนวทางพิจารณา |
|---|---:|---|
| Workflow และการเลือก specialist | 30 | ใช้ LangGraph และเลือก/เรียก specialist ตามลำดับ รวมถึงจัดการคำขอที่ไม่ตรง |
| ผลลัพธ์และ execution trace | 20 | แสดงผลจาก LLM และ trace ที่ตรวจสอบได้ รวมถึงสถานะเมื่อเรียกสำเร็จหรือล้มเหลว |
| ความปลอดภัยและข้อจำกัด | 20 | Calculator ใช้ restricted AST และปฏิเสธ input ที่ไม่อนุญาต ไม่ใช้ `eval`, `exec` หรือ shell execution และไม่เปิดเผย credential |
| การตรวจสอบและการส่งมอบ | 15 | มีคำสั่งติดตั้งและรัน มี mock test แบบออฟไลน์ และขั้นตอนตรวจการเชื่อมต่อ LLM จริงแยกต่างหาก |
| การใช้ AI และวิจารณญาณ | 15 | แสดง prompt ที่สำคัญและอธิบายวิธีตรวจหรือแก้ผลลัพธ์จาก AI รวมถึงข้อจำกัดที่ยังเหลือ |
| **รวม** | **100** | |

ให้คะแนนตามหลักฐานและส่วนที่ทำงานได้จริง หากส่งไม่ครบ ให้พิจารณาคะแนนบางส่วนตามแต่ละหัวข้อ

## สิ่งที่ให้ผู้สอบส่ง

1. ซอร์สโค้ด พร้อมคำสั่งติดตั้งและรัน
2. คำสั่งทดสอบหรือขั้นตอนตรวจสอบและผลที่ได้
3. Prompt หรือประวัติการใช้ AI ที่สำคัญ
4. คำอธิบายการตรวจหรือแก้ไขผลลัพธ์จาก AI และสิ่งที่ยังไม่สมบูรณ์
